# Copied ALAC tail preservation — 2026-09-30

## Reproduction and fix

Issue #321 reproduces with a freely generated 16-second, 48 kHz mono ALAC Matroska file.
It decodes to 768,000 samples. Copying to M4A/MP4 succeeds, but normal playback decodes
765,952 samples, losing the final partial packet's 2,048 samples (42.67 ms). Ignoring the
edit list recovers all 768,000: the compressed payload is present. Source packet timing
lacks a final duration and the copied MP4's edit duration ends at the last packet's start.
This is distinct from video encoder precision and subtitle timing.

The observation reproduces with the Mac's pinned FFmpeg n8.0.3, PICARD's installed n8.1.2,
and actual server/Linux-worker Jellyfin FFmpeg 7.1.4. Copying a kept ALAC track from Matroska
now selects MKV, preserving normal playback without globally disabling edit lists. ALAC
already encoded into MP4, audio re-encoding and removal of the ALAC track retain the chosen
target. Fresh probe order is used when deciding which copied tracks remain.

## Second-order review

An MP4-only remux could become an unchanged MKV copy after fallback. Known no-op candidates
are now skipped with a clear ALAC reason before enqueueing. A fresh-planning guard cancels
unchanged remuxes that reach preparation with unproven inventory. Actual encodes and track
removals remain eligible. The source audio summary is not treated as per-track identity.

The independent acceptance verifier selects only intentionally kept reference tracks before
comparing metadata and PCM hashes. Other cases still compare every track. New decoded-audio
reports retain both hashes. Production verification thresholds, edit lists and originals are
unchanged; this is a targeted planning safeguard, not a new general production PCM hash gate.
